# 架構原則

這份寫的是**長期成立的設計原則**：新功能放哪、元件之間怎麼連、哪些事絕不能做。
現在有哪些元件、各自在哪、怎麼部署，見 [系統導覽](system-overview.md)；
這些原則是怎麼被外部限制推出來的，見 [為什麼是 Home Assistant](why-home-assistant.md)。動手簡化之前先讀那份。

2026-10 重構時的每一項決定與理由在 [重構計畫](refactor-plan.md)。本檔是那些決定沉澱下來、之後仍要遵守的部分。
（本檔在 2026-10-22 之前是「家庭中樞架構與遷移順序」，記錄 2026-09 從直連設備逐台移到 HA 的過程；那段歷史在 git 紀錄裡。）

## 1. 分層

| 層 | 是什麼 | 不做什麼 |
| --- | --- | --- |
| Home Assistant（HA，家裡） | **唯一的設備層。**本地或只有雲端 API 的設備都只接在 HA；HA 的整合就是「接雲端設備」的節點，不另加節點。即時自動化、Apple 家庭的 HomeKit 橋接也在這裡 | 不存家庭資料、不排「之後會發生」的事 |
| HomeButler（HB） | **只當大腦**：家庭資料（成員、待辦、食品、排程）、LINE 管家、通知、Dashboard 的後端，以及 Notion、天氣、Claude 這類資料服務 | **不直接連任何設備**，永遠透過 HA 看和控制 |
| Dashboard | 家人的操作畫面 | 不存資料、不自己判斷規則；只經 HB |
| Apple 家庭 | Siri 與 Apple 生態的入口 | 不另走路徑，經 HA 的 HomeKit 橋接 |
| 本地專用服務（劇院、攝影機存在感測） | 有狀態、要在家裡跑的協調工作 | 對外只經 HA（劇院用 HA 整合、存在感測用 MQTT），HB 不直接連它們 |

例外只有兩個，都做成可以整個刪除的隔離模組，核心不直接引用：

- **除濕機**（`homebutler/dehumidifier/`）：之後會淘汰，不值得搬進 HA。
- **SwitchBot 推送轉交**：SwitchBot 雲端只能打到公開網址，HA 沒有，所以暫由 HB 收、只轉「去重讀」的提示給 HA。HA 有對外網址後改成直接通知 HA，刪掉這個模組。

## 2. 新功能放哪：HA 還是 HB

先問：**這件事家人需不需要事先知道、或能自己調整？**

- **需要** → 做成 HB 的排程或規則，在 Dashboard 顯示、可修改。原因是大部分家人用的是 Dashboard，不是 HA；之後會發生的事沒有畫面可看，很容易被漏掉。
  例：客廳冷氣早上 7 點關，做成 HB 每次開機排一筆 07:00 的關機排程，而不是 HA 自動化。
- **不需要、純粹即時反應** → 寫成 HA 自動化。本地執行、反應快、斷網也能用。
  例：有人就開燈、沒人就關燈。

**同一台設備、同一條規則，同時間只能有一個控制主體。**不要兩邊各做一份，也不要形成 HB → HA → HB 的循環指令路徑。

## 3. 每個模組都要換得掉

任何一台主機或一個雲端服務都不能變成「拿掉就要改架構」的前提；換的時候只是搬家。

- **程式只寫「找誰」，不寫「在哪」**：模組之間靠設定裡的網址找彼此。能讓對方主動連進來的就這樣做：HA 主動以 WebSocket 連到 HB，所以 HB 換位置時 HA 不需要有對外網址，只改整合裡的網址。
- **對外入口的網址要換得掉**：HB 換位置時要改的地方是 LINE 的 webhook、Dashboard 的後端網址、HA 整合的網址、外部監控。自己的網域只是讓這些不用改的便利工具，不是前提。
- **資料換得掉**：資料層只用 SQLite 與 PostgreSQL 都支援的寫法（本機測試用 SQLite、CI 用 PostgreSQL 跑同一套），換資料庫只改連線字串；每天匯出一份通用格式的備份到主機以外的地方。
- **同一種方式啟動**：結構版本由 Alembic 在啟動時自動套用；所有設定集中在 `settings.py`，值不對就停並說出變數名。換主機照清單重填設定即可。
- **硬體綁定的部分要有退路，但不預先寫兩套**：真的要換時再補。
- **不為了彈性過度設計**：不把模組拆更細、不導入 Kubernetes 之類的工具。平常多花一點點，換的時候省很多。

## 4. 狀態要誠實

- **未知不是關。**HA 斷線、資料過期、指令結果不明時，畫面與管家都說「未知」，不猜。
- **結果不明的指令不自動重送**，重啟後也不補送；留給人去看設備。
- **不 fallback 到另一條路徑**：HA 斷線就拒絕或等，不改走雲端或直接送紅外線。
- 「指令被接受」「最後送出的指令」「實際觀察到的狀態」是三件事，分開記錄、分開顯示。
- 沒有簽章的外部內容（例如 SwitchBot 推送）只能當「去重讀」的提示，不能直接寫成狀態。

## 5. 戶別

系統會管理兩戶（同一個區域網路、同一台 HA）。

- **戶別以 HA 的「樓層」為準**：每個區域掛在所屬樓層下，其他地方讀它，不另外維護一份。
- HB 每張家庭資料表都有戶別欄位；Dashboard 的過濾做在後端，不是只把介面藏起來。
- 「目前顯示哪一戶」是便利功能，不是權限：任何人都能選；自動判斷只是盡量先切到對的那一戶，判斷不了就維持上次的。
- 家人共用的顯示設定（例如房間順序）存在 HB、按戶別各一份，不存在各自的手機裡。
- **切換戶別時什麼跟著換**（使用者 2026-10-23 同意）：
  - 跟著「目前選的那一戶」：設備、空間感測、歷史圖、排程與自動關機、房間順序、照明區域、食品庫存（每戶有自己的冰箱）。
  - 跟著「人」、不隨切換改變：個人待辦（自己的與公開的）。待辦的燈光提醒亮待辦主人所屬那一戶的燈。
  - 還沒定：公開待辦只給同一戶的人看，還是全家都看得到。
  - 目前戶別是每個登入裝置的狀態，由 Dashboard 隨身分簽章送給 HB；HB 只確認那一戶存在，不當權限檢查。成員所屬的戶只是預設值。
- **現況（2026-10-23）**：地基已在（戶別表對應 HA 樓層、各家庭資料表有戶別、設備依樓層自動歸戶；待辦、食品、照明區域、房間順序已按成員所屬的戶過濾）。
  還沒做、等接 B 戶時一次做完：裝置頁的設備與空間感測、歷史圖、排程與自動關機、待辦頁的成員清單按戶過濾；「目前戶別」與 Dashboard 的切換介面；HA 分樓層與兩個 HomeKit 橋接器。
  在那之前新增的功能就照上面的規則寫（新查詢帶戶別條件）。

## 6. 多台攝影機

每台攝影機各自畫區域、各自送出感測器，重疊也沒關係；**同一個空間的合併在 HA 用群組做**（任一有人即有人），不做在攝影機的服務裡。
感測器名稱要帶相機來源以免撞名，並且要有辦法看出某台相機離線（群組會因為另一台正常而照常運作，看不出涵蓋變小）。
